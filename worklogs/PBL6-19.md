# PBL6-19 — Payment Service

Branch: `PBL6-19-payment-service`, PR target: `dev`.

Implements FR-PAY-01..05 and the narrow Order/Gateway integration needed for payment results,
expiry and inventory release. No frontend/mobile, Docker or teammate service implementation.

- Trusted order amount, fixed 15-minute expiry, stable PayOS order codes, server callback URLs.
- HMAC webhook validation, row locks, unique references and duplicate-safe transitions.
- Buyer-only transaction history; COD recording; Admin manual refund request/confirmation audit.
- Order stock reservation events, payment success/failure consumers and expiry without a payment request.
- SQL outboxes retain events when publication fails; cancellation/success races reconcile refunds.

PayOS credentials are not configured in the inspected project. PayOS officially has no sandbox:
https://payos.vn/docs/moi-truong-test/. Live PayOS verification remains open and must not
be represented as sandbox acceptance. Automated tests use a mocked provider and H2.

Reviewed by `gpt-6-astra` with reasoning `medium`, then re-reviewed after fixes.
Final review: no actionable findings remaining. Fixed row-lock races, broker ACK/return
handling, missing-QR fallback, COD cancellation tombstones, cancellation retry starvation
and persistent reconciliation when PayOS reports PAID without the bank webhook.

Validation: Maven reactor BUILD SUCCESS, 99 tests passed (shared-events 14,
api-gateway 39, order-service 17, payment-service 29), zero failures/errors/skips.
Tests include real concurrent H2 transactions, actual Flyway schema migration,
loopback HTTP provider protocol and asynchronous broker nack/return/timeout simulations.
This does not prove real PostgreSQL concurrency, a live bank payment, or a deployed workflow.

owner to update that build context/dependency setup. Dockerfiles/Compose were deliberately
